# Peak shaving — implementation report

Branch `feat/peak-shaving`. Baseline confirmed before starting: `npm run check`

## Per-file changes

### `src/core/config.js`
Added to `CONFIG.buildings.ups`:
- `rechargeKw: 10` — the draw while topping off, billed like any load.
- `roundTripEff: 0.9` — the fraction of that draw that actually lands in the
  buffer; the rest is heat/conversion loss.

These two numbers were chosen so `rechargeKw * roundTripEff / capacityKw =
9/36 = 0.25` — **exactly** the pre-existing free-recharge rate (`dt/4`).
Recharging still refills the buffer at the pace it always did; only whether
it costs anything changed. `roundTripEff = 0.9` was chosen (rather than some
other value < 1) because it is a clean number that reproduces the pinned
`0.25` rate with a clean `rechargeKw = 10`, and it lands the worked economics
inside the task's own stated range (see below) — it was not tuned against
any test result, only against the physical-consistency requirement and the
plausible range for a real UPS/battery round trip.

### `src/core/state.js`
- `STATE.batteryKw` — kW of `totalDrawKw` sourced from a UPS buffer this
  tick (peak shaving), owned by `sim/power.js`, written every tick. Added to
  the STATE literal and to `resetState()`.
- `STATE.peakShave = { on: false }` — the player toggle. Added to the STATE
  literal and to `resetState()` as a fresh literal.
- Checked `tests/crisis.test.mjs`'s "resetState clears every crisis and
  contract field back to virgin" test: it does exact-literal `toEqual` on
  `brownout`/`breakdown`/`contract` only, not the whole STATE object, so it
  did not need updating.

### `src/entities/Building.js`
- `this.upsMode = "idle"` — per-building status (`"idle" | "charging" |
  "shaving" | "bridging"`), owned by `sim/power.js`, read by the inspect
  panel so it never has to re-derive direction of travel from `bufferLeft`'s
  trend (charging and shaving both move the number the same way).

### `src/sim/power.js` (the mechanic)
In `deliver()`'s UPS clause: peak shaving is a new branch checked **before**
the existing recharge branch, gated on `STATE.peakShave.on && outLive &&
b.bufferLeft > 0`. `outLive` is the value passed down from the parent
*before* the UPS's own self-grant logic can set it — so this branch can never
fire during a genuine outage (`outLive` is false there), which is what keeps
the existing outage bridge untouched.

- **Shaving**: `outKw = pull` (bypasses `grantKw` from upstream entirely,
  same as the existing self-grant does), drains `bufferLeft` by `dt` while
  `pull > 0` (identical drain formula to the existing outage bridge), and
  adds `outKw` into a per-tick `batterySum`.
- **Recharging** (the `else if (outLive)` branch, reached whenever not
  shaving): now computes `wouldAdd = (rechargeKw * roundTripEff * dt) /
  capacityKw`, clips it to the room left in the buffer, and bills exactly the
  grid draw that produced the actual (possibly clipped, on the last partial
  tick) amount added — into a per-tick `rechargeSum`. No energy is ever
  billed that didn't charge anything.
- At the end of `resolvePower`: `STATE.totalDrawKw = itKw + coolKw +
  rechargeSum` (recharge now counts as real facility draw — same bucket a
  CRAC's idle draw already lives in) and `STATE.batteryKw = batterySum`.
  `totalDrawKw` still means "total facility draw" and is still what PUE is
  computed from in `src/ui/hud.js` — it legitimately rises while a UPS
  recharges, which is honest (recharging a UPS really does cost facility
  overhead), and only the **money meter**, not PUE, is what shaving touches.

### `src/sim/demand.js`
`tickDemand`'s power-cost line now bills `Math.max(0, STATE.totalDrawKw -
STATE.batteryKw)` instead of `STATE.totalDrawKw`. This is the only place the
battery subtraction happens — `totalDrawKw` itself is never rewritten to mean
something different.

Baseline on entry: `npm run check` green, 19 files, 324 tests, HEAD 56d611d.
Final: green, 19 files, **340 tests**.

Three commits:

| SHA | What |
|---|---|
| `277ddd3` | the UPS battery is energy, and the energy has to balance (C1, C2, I1, I2, I3, I4, I5, MINOR) |
| `7cac3ff` | a tripped UPS is isolated, not shaving |
| `851328e` | a shaving UPS above a charging one was deleting the difference |

The second and third were found by mutation-testing the first. Both are
written up under "Mutation list" rather than hidden in the per-finding notes,

## CRITICAL 1 — the mechanic manufactures energy

The review was exactly right, and the reproduction matched to the cent:
`+$26.17` over 120 s at `multiplier = 1`, `+$119.77` over 600 s, and a
measured round trip of **457%**.

The fix is not a clamp bolted onto the old grant — the grant itself was
denominated in the wrong unit. A buffer-second is defined as one second of
`capacityKw` draw, so the battery holds `capacityKw * bufferSec` = 288 kW.s.
Peak shaving now spends it in that currency:

```js
const displaceable = served - battOut;              // grid kW we can replace
const wantSec = cap > 0 ? (displaceable * dt) / cap : 0;
const useSec = Math.min(wantSec, b.bufferLeft);     // only what is in there
const fromBattery = (useSec * cap) / dt;
b.bufferLeft -= useSec;
b.bufferOwedKws += fromBattery * dt;
battOut += fromBattery;
```

Three things changed together, which is what the review meant by "the buffer's
energy content, `batterySum` and the bill must agree":

- **The grant is capped by the charge left.** When the battery holds less than
  the tick wants, the shortfall is not forgiven — the grid quietly carries the
  remainder. `outKw` is untouched, so the racks are still served in full; only
  the *source* of those kW changes. That is the honest reading of what shaving
  is, and it removes the `Math.max(0, ...)` that was papering over the overdraw.
- **The drain is proportional to energy delivered, not to wall-clock.** A UPS
  delivering 4 kW spends 4 kW.s per second, not 36. This is a deliberate
  divergence from the outage bridge, which still spends a second of buffer per
  second whatever it carries — see "What I did not touch" below.
- **`bufferOwedKws`** (new, `entities/Building.js`) records the energy that
  actually left, and the charger works it back down. That single field is what
  makes I1 and the audit possible.

### The energy audit

600 s machine-played run, 36 kW room, toggle left ON the whole way, flat meter.
`stored` is measured as the per-tick decrease in `bufferOwedKws`; `out` is
`batteryKw * dt` summed; `bought` is `stored / roundTripEff`.

```
 120s  out   489.4 kW.s  stored   201.6  bought   224.0  | out/(initial+stored) 100.0%  marginal out/bought 89.9%
 600s  out  1353.4 kW.s  stored  1065.6  bought  1184.0  | out/(initial+stored) 100.0%  marginal out/bought 90.0%
1200s  out  2433.4 kW.s  stored  2145.6  bought  2384.0  | out/(initial+stored) 100.0%  marginal out/bought 90.0%
1800s  out  3513.4 kW.s  stored  3225.6  bought  3584.0  | out/(initial+stored) 100.0%  marginal out/bought 90.0%
```

Was 457%. Now **100.0% of what was in the battery**, and the *marginal* round
trip — everything after the charge the UPS was built with — is **90.0%**,
`roundTripEff` to three decimals. Both are pinned as tests
("CONSERVATION: what came out equals what was stored plus what the battery is
still short", "the MARGINAL round trip is roundTripEff").

The reviewer's own two-tick pump is pinned directly too: one tick of charger
output buys 0.5 kW.s and stores 0.45; the next tick hands back **0.45 kW.s**,
not the 1.8 it used to.

### The flat-tariff result with the toggle left ON for the whole run

The "THE LESSON" test no longer releases the toggle at `bufferSec` — it is
simply on for the entire run, which is all the button lets a player do.

```
THE LESSON: toggle left ON, flat meter, 30 kW room, 1200 s
  shaved 1255.30   control 1259.91   delta -4.61   buffer left 0.0000 vs 8.000
```

**Shaving loses.** It also ends with an empty battery against the control's

One thing the reviewer should know, because it is visible at short horizons
and I did not want to bury it: **over the first ~700 s the toggle-on run is
still ahead**, by up to $3.98 at 120 s. That is not manufactured energy — the
audit above proves the round trip is 0.900 — it is the 288 kW.s (4.8 kWh,
$4.32 at a flat meter) that a UPS is *born* holding, spent once. A newly built
UPS starting flat would remove it, but it would also mean a UPS cannot bridge
the outage it was bought for until 32 s after placement, which moves
`dark_chain` and `fuel_clock`. I left the free initial charge alone and sized
the test past the crossover instead. The steady-state loss rate is
`(1 - roundTripEff) * chargerKw / 2` = 0.5 kW, dt-invariant.

## CRITICAL 2 — `batteryKw` double-counted through UPSes in series

`batterySum` is no longer incremented at each UPS. `deliver()` now carries a
fourth argument, `grantBattKw` — the battery-sourced share of a grant — down
the chain, and the credit is banked **at the loads**, the only place a kW is
counted exactly once. A UPS also only ever displaces the *grid-sourced* part
of what it is delivering (`displaceable = served - battOut`), so a UPS under a
shaving UPS has nothing left to displace and keeps its own charge.

Reviewer's exact repro, now a test:

```
feed -> ups -> ups -> pdu -> 2 racks   (8 kW)
feed -> pdu -> rack                    (4 kW, no battery anywhere)

totalDrawKw 12   batteryKw 8   billed 4      (was: batteryKw 16, billed 0)
upsB.bufferLeft === bufferSec — the inner UPS did not dump its battery for nothing
```

The un-buffered chain no longer rides free. The marquee economics test also
grew a 6 kW un-buffered rack (the MINOR item), and a second test asserts
`totalDrawKw - batteryKw === 6` on every tick while shaving — an inflated
credit now shows up as an under-bill instead of vanishing into the clamp.

## IMPORTANT 1 — PUE, and the `pue_hold` contract

`rechargeKw: 10` is gone. The charger is sized from the UPS's own capacity:

```js
rechargeRate: 0.25,     // share of capacityKw that LANDS in the battery per second
roundTripEff: 0.9,      // draw = capacityKw * rechargeRate / roundTripEff = 10 kW here
```

and — the substantive half — it restores **the energy that actually left**
(`bufferOwedKws`) instead of a nameplate refill. Seconds come back in step
with the energy, so both reach full together however deep the discharge.

A UPS that bridged a 12 kW room for 8 s gave up 96 kW.s, not 288. It used to
buy back 288/0.9 = 320 kW.s over 32 s; it now buys back 107 kW.s over ~13 s.

```
dark_chain lean, toggle OFF:
  baseline PUE 1.250, peak PUE during recharge 2.083
  seconds above 1.35 across all three outages: 19.9 s   (was 3 x 24 = 72 s)

pue_hold (windowSec 75, holdSec 45, pueBelow 1.35), worst case — contract
offered the instant the lights come back, whole recharge still ahead:
  new: clean streak available 61.65 s  >= 45  => WINNABLE  (machine-played to done === "paid")
  old: recharge 32 s -> 75 - 32 = 43   <  45  => UNWINNABLE
```

**Honest caveat:** the *peak* PUE is still 2.083. I did not reduce the
charger's instantaneous draw, because a charger is a constant-power device and
inventing a taper rate to hit a PUE number is the config retune CONTRIBUTING
warns about. What changed is the excursion's duration (3.6x shorter) and the
energy billed (3x less), which is what made the contract unwinnable. If the
peak itself is the objection, the lever is `rechargeRate`, and it should move
with the level pairs re-run — I did not move it.

## IMPORTANT 2 — recharge billed by a dead utility, never burning fuel

The charger is now a load on the chain. `pullOf()` folds `rechargeReqKw` into
what the UPS reports upward (on top of its output rating — `capacityKw` is an
output rating, the charger hangs off the input side), so every link above
carries and clips it, and a generator burns fuel for it. `demandedKw` and
`clippedKw` stay output-side so a charger cannot trip the UPS's own breaker.

Three tests, one per requirement:

- **Clipped by upstream capacity** — 24 kW of racks under a 30 kW transformer
  leaves 6 kW, so the 10 kW charger gets 6 and the transformer pins at its
  rating (`totalDrawKw` 30, not 34).
- **Burns generator fuel** — `g.actualKw === racks + chargerKw` while charging,
  and the fuel burned over the window matches that number, not the racks alone.
  On `fuel_clock`'s WIN build the generator now burns 2.025 L carrying the
  recharge.
- **Does not recharge when upstream is dead** — 200 ticks with the feed gone:
  `bufferLeft` never rises, `upsMode` is never `"charging"`, and
  `totalDrawKw - itDrawKw` stays at 0. Not one kW of charger on the meter.

**A bug fell out of this.** The ancestor-UPS fixup also restored a UPS that the
standby wave had *itself* re-delivered, undoing the charge it had just taken
from the generator. It sat pinned at the same `bufferLeft` for the whole

21.90 s recharging while `gridOutage.active === true`" the review measured. It
was never going to finish. The fixup now skips nodes in `redelivered`.

**Residual I am not fixing, flagged rather than hidden:** on `fuel_clock`'s WIN

### Two bugs the mutations found

**A tripped UPS was not declining to shave** (`7cac3ff`). Mutation 3's green

zeroes the delivery, a per-UPS credit has already been banked for kW that

test; the guard I first added inside the clause turned out to be unreachable

than ship a comment claiming a line was load-bearing when it was not.

# Charger fix — the same class, in the other direction

The re-review passed the last change and found two more defects of the same
class still live at `9a709bd`, both in and around `deliver()`. Both are on the
CHARGER side, which is why the invariant added last commit never saw them: it
only ever compared the credit against the energy that LEFT a battery.

Both reproduce with the toggle OFF. The charger runs with the toggle off, so
these are corrections to the toggle-off baseline, not to the mechanic.

## Fix 1 — `rechargeSum` was a running `+=` in a function the wave calls twice

The previous commit message claimed `battCredit` "was the only number in the
function that added where the rest assigned". That was wrong. `rechargeSum`
added too, and the standby wave re-enters `deliver()` for a transferred
subtree, so a UPS that charged on pass 1 had its buffer rolled back to
`bufSnap` and charged AGAIN on pass 2 — with both passes on the meter.

The fix is the same shape the credit already got: `chargerDraw`, a `Map` keyed
by the UPS, cleared at the top of `deliver()` alongside `battCredit.delete`,
`set` where the charge happens, summed once at the bottom of the tick. Nothing
new on `STATE` or on `Building`; the map is local to `resolvePower`, so
`resetState()` has nothing to learn. Assignment semantics is the whole point —
it is what every other per-node result of `deliver()` already does.

I deliberately did NOT make the ancestor fixup revoke a restored node's
`chargerDraw` entry as belt-and-braces. It would paper over fix 2 instead of
letting the assertion catch it.

## Fix 2 — the ancestor-UPS fixup restored a UPS that was never bridging

`feed(LIVE) -> upsX -> transformer(out for service) -> pdu -> racks` with
`generator --standby--> pdu`. `upsX` is on live utility power, legitimately
charging. Its subtree's primary path is dead — but the death is BELOW it, not
above. It "carries nothing outside the redelivered set", so the fixup restored
its snapshot every tick: the charge was rolled back and the bill was not.

`node.upsMode === "bridging"` is the right gate, and I checked it against how
`upsMode` is actually written rather than taking it on trust:

- it is assigned on every visit to a UPS in `deliver()`, and phase 4's final
  sweep visits every unvisited node, so it is never stale from a prior tick;
- `"bridging"` is set on exactly one branch — `outLive === false &&
  bufferLeft > 0` — which is the only path that self-grants `subtreePull` from
  the buffer. That is precisely the drain this fixup exists to undo;
- the two neighbouring states are correctly excluded: `bufferLeft <= 0` on a
  dead path reads `"idle"` and drained nothing (restoring it is a no-op), and
  `subtreePull === 0` reads `"bridging"` but skips the drain (also a no-op);
- and it protects the LEDGER too — a *shaving* ancestor restored by this
  block would have had its discharge deleted while its credit stayed on the
  meter.

## Fix 3 — THE MIRROR

`tests/peak-shaving.test.mjs`, in the same `THE LEDGER` describe and on the
same 200 s facility: every tick, **billed charger draw ≤ energy that landed in
a battery ÷ `roundTripEff`**.

Billed charger draw is read as `totalDrawKw - Σ(load actualKw)` — no test-only
field, and it reads the same number a broken implementation publishes, which is
what lets the same assertion run against the mutants. Landed energy uses the
same two-books rule as the LEDGER (`min` of the charge book and the debt book),
which is exact here: `restored / roundTripEff` is what the charger draws, so
the invariant has **zero slack** — it is an equality that has been written as
an inequality. A count of the nameplate-refill fallback (`owed === 0` with
seconds missing, where the two books would disagree) is asserted to stay 0, so
if that path ever becomes reachable the test names the assumption that broke.

The facility grew two branches, because the old one could not reach either
shape. Both new blackouts are **scoped to substation B**, so the A-side
branches the existing LEDGER test measures are untouched:

```
grid_feed -> ups -> transformer -> pdu -> 2 racks   the ancestor case
generator --standby--> that pdu                     (fix 2)

grid_feed -> ups -> ups -> pdu -> 2 racks           a charger inside a
generator --standby--> the upper ups                re-delivered subtree (fix 1)
```

Fix 1's shape only lines up when the upper UPS is STILL BRIDGING as the cutover
completes — that is what keeps the lower one live on pass 1 — so that branch
gets an earlier blackout of its own: a bridge books far less debt per second of
buffer than shaving does, so a room that has already been through a blackout
recovers its SECONDS fast enough to still be carrying when the transfer switch
lands. Both shapes are asserted to have been reached (`reDeliveredCharger > 0`,
`ancestorCharger > 0`), so green cannot mean the scenario stopped visiting them.

## Per-UPS vs facility-wide, and the slack the reviewer named

Measured on the run above with a **25% credit inflation injected** at the loads:

```
CLEAN         creditTicks 2900  caughtByFacilityWide 0     caughtByShavingOnly 0
+25% INFLATED creditTicks 2900  caughtByFacilityWide 2582  caughtByShavingOnly 2900
              ticksWithSlack 318  slackKws 321.378
```

So the slack is real: 321 kW.s over 318 ticks, and it masked the inflation on
exactly those 318 ticks.

I did **not** make the LEDGER per-UPS. A load's credit is a proportional clip
of a battery share that may be mixed from two UPSes in series, so attributing
it back to its source means threading originating ids through `grantBattKw` —
production complexity added for a test's benefit, in the one function on this
branch that has now been wrong four times.

Instead the creditable pool is restricted to the UPSes that actually SHAVED on
this tick's last resolution. That is sound rather than approximate: every
credited kW traces to the shaving branch (a root grants `grantBattKw` 0, the
bridge sets `outBattKw = 0` explicitly, nothing else adds), so a UPS in any
other mode is contributing energy the meter was never credited for. It removes
100% of the measured masking — 2900 of 2900 — with zero false positives on the
clean run, and mutation 3 below confirms it did not loosen the existing guard.
